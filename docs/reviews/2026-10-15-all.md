## Summary

The code is in good health. The layering is clean: the spec's rules live in `src/lib/`, pages are thin, and nearly every rule has a test named after it. Decisions 54 to 72 are carried through to code and tests. The biggest risk is in the edges of End Chapter (spec 5.4, decision 50). The design promises that a failure at any step loses nothing, but two write sequences can leave the story in a state the app cannot leave: one failed `story.json` write blocks the story for good (CR-01), and one failed write after the chapter summary skips the review (CR-03). The second risk is the AI boundary: a stream that closes cleanly in mid-block, or stops at the provider's output limit, is saved as a finished block (CR-02). Not reviewed: anything only the real Tauri build shows (see the last section), and the CSS beyond the paragraph rule.

## Findings

### CR-01 · Major · One failed `story.json` write at End Chapter leaves the story unable to start the next chapter

- **Where:** `src/lib/endChapter.ts:326-331`, `src/pages/NovelTab.tsx:192`, `src/lib/draft.ts:45-46`
- **Contract:** spec 5.4 ("Closing the app during the review loses nothing"), decision 50
- **Problem:** `endChapter` writes `chapter.md`, then raises `chapterCount` (and sets `ending` for an accepted death) in `story.json`. If that second write fails, or the app closes between the two writes, the page shows "summary pending". Its Retry button calls `summarizeChapter`, not `endChapter`, so `chapterCount` is never raised. After Finish, `emptyDraft` opens chapter `chapterCount + 1`, which is the chapter that already ended. Every Start then fails with "Chapter N has ended and can no longer be changed." An accepted death is also lost, so the story never reaches its epilogue.
- **Breaks when:** On Windows, an antivirus or OneDrive sync briefly locks `story.json` (EPERM) during End Chapter, or the app is closed during that step. Proven in `test-results/review/review.test.ts`, first test. The only way out is to edit `story.json` by hand.
- **Suggested fix:** Make the step that comes after a failure repair the state. For example, `summarizeChapter` (or `loadNovelState`) can raise `chapterCount` to at least the highest ended chapter. Or `emptyDraft` can take the next chapter from `listChapters` instead of from `chapterCount`. The death `ending` needs a durable home written before `chapter.md`, such as `draft.json` or the chapter folder. `docs/tech/data-and-storage.md:150` currently says that "a retry after a crash is safe".
- **Test to add:** U-EC: a `story.json` write that fails after `chapter.md` is saved, followed by Retry and Finish, still opens chapter N+1 and keeps `ending: death` (spec 5.4, decision 50).
- **Status:** Fixed 2026-10-15 (decision 75). `reconcileStory` in `endChapter.ts` repairs `chapterCount` and `ending` on page load and in `finishChapter`; the ending is saved in `draft.json` before `chapter.md`. Three U-EC tests.

### CR-02 · Major · A stream that closes early, or is cut off at the provider's output limit, is saved as a full block

- **Where:** `src/lib/ai.ts:285-286` (`if (done) return text;`), `src/lib/ai.ts:204-207` (`StreamChunk` ignores `finish_reason`)
- **Contract:** spec 5.1 ("The draft is autosaved after every block, and only when a block has arrived in full"), decision 38
- **Problem:** `streamChat` treats a stream that ends without `[DONE]` as complete. It also never reads `finish_reason`, so `"length"` (the output was cut off) counts as success. A truncated answer has no `=== NEXT ===` marker, so `parseBlock` keeps it as story text with no actions (decision 37), and `writeBlock` saves a block that ends mid-sentence. The user must notice and regenerate. The mock server only drops connections with `res.destroy()`, so E2E-12 and E2E-21 never cover this case.
- **Breaks when:** A proxy or server timeout closes the HTTP stream cleanly mid-block, or the provider's default `max_tokens` is smaller than the block. The second case is common with reasoning models, whose hidden tokens count toward the limit. Proven by the third and fourth throwaway tests: `"Lin Feng climbed the stairs and reached for the"` is saved as a block.
- **Suggested fix:** Record the last `finish_reason`. Treat `"length"` as an `AiError` ("The provider cut the block off at its output limit…"), and treat a stream with neither `[DONE]` nor a `finish_reason` as broken off. The JSON-body branch (`ai.ts:235-247`) can check `choices[0].finish_reason` the same way. Keep the "no [DONE]" tolerance only when a `finish_reason` of `"stop"` arrived.
- **Test to add:** U-AI: a stream with `finish_reason: "length"`, and a stream that ends with neither `[DONE]` nor `finish_reason`, both throw, and the draft is unchanged (spec 5.1, decision 38). Add a mock key that sends half a block and then calls `res.end()`.
- **Status:** Fixed 2026-10-15 (decision 74). `streamChat` keeps the last `finish_reason`; U-AI and U-NV tests, and mock keys `sk-test-stream-cut` and `sk-test-stream-length` in E2E-21.

### CR-03 · Minor · A failed write after the chapter summary skips the review and keeps the old "story so far"

- **Where:** `src/lib/endChapter.ts:382-390`
- **Contract:** spec 5.4 ("The AI's answer is saved as soon as it arrives… Closing the app during the review loses nothing"), decision 50
- **Problem:** `summarizeChapter` writes the chapter's `summary.md` first. That file is the marker `loadNovelState` uses to switch from "summary pending" to "review". The story `summary.md`, `scenes.md` and `review.json` are written after it. If any later write fails, the page shows the review with no proposals, because a missing `review.json` reads as an empty list. Finish is enabled at once. The "story so far" never gets this chapter, and the proposals are gone.
- **Breaks when:** The disk fills up, or a file is locked, on the second of the four writes. Proven by the fifth throwaway test.
- **Suggested fix:** Write the chapter `summary.md` last, since it marks the step as done. Or make `loadNovelState` require `review.json` before it shows the review.
- **Test to add:** U-EC: a write that fails after the chapter summary still leaves the chapter "summary pending", and Retry produces the proposals (spec 5.4).
- **Status:** Fixed 2026-10-15 (decision 76). `summarizeChapter` writes `review.json`, `scenes.md` and the story summary first and the chapter `summary.md` last. One U-EC test.

### CR-04 · Minor · Approving the same new-character proposal twice writes two character files

- **Where:** `src/lib/endChapter.ts:404-428`
- **Contract:** spec 7.5, spec 5.4 ("Approving a proposal writes it to the character file at once")
- **Problem:** `approveProposal` does not check that the proposal is still pending. For `kind: "new"` it calls `saveCharacter` with `id: ""`, which makes a new id every time. If `saveCharacter` succeeds but `saveReview` (inside `answer`) fails, the card stays pending, and the user's second Accept creates a second "Elder Wu". The same happens if "Edit first" saves the character but `markAccepted` fails.
- **Breaks when:** A write error between the two saves, followed by Accept again. Proven by the second throwaway test, which calls `approveProposal` twice.
- **Suggested fix:** Return early when `proposal.status !== "pending"`. For new characters, also refuse a name that already exists, as `checkProposals` already does when it builds the list.
- **Test to add:** U-EC: approving an answered proposal changes nothing, and accepting a new character whose name now exists is refused (spec 7.5).
- **Status:** Fixed 2026-10-15 (decision 78). `approveProposal` returns the review unchanged for an answered proposal and refuses a new character whose name exists. Two U-EC tests.

### CR-05 · Minor · Leaving the story during the End Chapter call does not ask, and Retry can then start a second call

- **Where:** `src/pages/StoryWorkspace.tsx:41`, `src/pages/NovelTab.tsx:183-197` and `:219-221`
- **Contract:** spec 9 (asks before leaving while a block is written), decision 59, spec 5.4
- **Problem:** The leave guard covers Setting edits and block streaming (`writing`), not the End Chapter call. That call runs in the `Novel` component's `run` and cannot be stopped. The user can leave while it runs and come back before it finishes. The page then shows "summary pending" with an active "Try the summary again", which starts a second call. Whichever call finishes last overwrites `review.json` with fresh pending proposals and new ids. If the second call began after the first saved the story summary, it sends that summary as the one "before this chapter", so this chapter is summarised into it twice.
- **Breaks when:** The user ends a long chapter, clicks "← All stories" during the 20–60 s call, reopens the story and clicks Retry. Unconfirmed in the browser; follows from the code.
- **Suggested fix:** Count the End Chapter call as "writing" for the leave guard, and pass it an `AbortSignal` (`summarizeChapter` already accepts one). Or hold a per-story in-flight flag in `src/lib` that refuses a second call.
- **Test to add:** E2E: leaving during End Chapter asks first; after leaving and coming back, Retry is not offered while the first call is still running.
- **Status:** Fixed 2026-10-15 (decision 77). The End Chapter call counts for the leave guard and leaving aborts it; `summarizeChapter` refuses a second call per story, and the page waits for one still running (`summaryInFlight`). Two U-EC tests and E2E-33.

### CR-06 · Minor · Only Chinese stories are told to phrase suggested actions as actions, not requests

- **Where:** `src/lib/prompt.ts:164`, `src/lib/languageStyle.ts:45`
- **Contract:** spec 6.5 bullet 3, decision 70 ("Suggested actions and chapter openings are phrased as what the main character does, never as a request")
- **Problem:** The End Chapter prompt asks every language for openings phrased as actions, not requests (`endChapter.ts:216`). For blocks, the "start with the name or the action, never a request" note comes only from `NOTES[language].action`, which exists only for the two Chinese labels. English, Malay, Japanese and Korean blocks only get "suggested actions for what the main character could do next". That wording allowed the "Have Chen Mei…" style that decision 70 was written to stop.
- **Breaks when:** An English or Japanese story gets actions such as "Have Lin Feng confront the elder".
- **Suggested fix:** Put a general action-phrasing line in the block answer format for every language, and keep the Chinese notes as extras.
- **Test to add:** U-PR: the block instructions for English and for a typed language ask for actions that start with the main character's name or a verb, never a request (spec 6.5).

### CR-07 · Minor · Regenerating a block clears the direction typed for the next block

- **Where:** `src/pages/NovelTab.tsx:371-372`
- **Contract:** decision 59 (typed, unsent text is kept; "a written block clears them")
- **Problem:** After any successful `run`, regenerate included, both the hint and the direction are cleared. A user who typed a long direction and then regenerated the current block first loses the direction. The regenerate never sent it.
- **Breaks when:** The user types a direction for the next block, then clicks "Regenerate block" with a hint.
- **Suggested fix:** On regenerate, clear only the hint. Clear the direction only when a new block was appended.
- **Test to add:** E2E-23 extension: a direction typed before a regenerate is still in the box afterwards.

### CR-08 · Minor · Unsaved pinned notes and character edits are lost without a question when leaving the story

### CR-09 · Minor · "Has appeared in a chapter" matches part of a word, so some characters cannot be deleted

### CR-10 · Minor · Rank ladder stages split only on the ASCII comma

- **Where:** `src/components/FieldForm.tsx:277`
- **Contract:** spec 8.3 (ladder of ranks, each with sub-stages); text handling for Chinese stories (decision 13)
- **Problem:** Stages are split with `split(",")`. A Chinese user who types `初期，中期，後期` with the full-width comma gets one stage named `初期，中期，後期`. The rank options, and so the characters' rank choices, become `煉氣, 初期，中期，後期`.
- **Breaks when:** Any ladder typed with a Chinese IME, where `，` is the default comma.
- **Suggested fix:** Split on `/[,，、]/`.
- **Test to add:** U-FD (or the component): a ladder typed with `，` or `、` gives separate stages.

### CR-11 · Minor · File writes in the app are not atomic; a crash mid-write can corrupt `draft.json`

- **Where:** `src/lib/storage.ts:49-54`
- **Contract:** spec 5.1 (autosave), decision 50 ("closing the app at any step loses nothing")
- **Problem:** `writeText` calls `writeTextFile` directly, which truncates and then writes. `draft.json` is rewritten after every block. If the app is killed or the power fails mid-write, the next `loadDraft` throws "draft/draft.json could not be read", and the chapter in progress is gone unless the user can repair the JSON. `isSettingLocked` (`setting.ts:69`) also reads a corrupt draft as unlocked. `docs/tech/data-and-storage.md:156` already flags this as unclear. Unconfirmed: it needs the real Tauri build and a forced kill during a write.
- **Breaks when:** A power cut or forced close during a block save.
- **Suggested fix:** Write to `<path>.tmp`, then `rename` over the target (plugin-fs has `rename`). At minimum, do this for `draft.json`, `review.json` and `story.json`.
- **Test to add:** Manual check in the phase file. In unit tests, assert that `TauriStore.writeText` goes through a rename, behind a mocked `@tauri-apps/plugin-fs`.

## Structure notes

- **Lifecycle state is spread across files with no repair step.** "Which chapter is next" comes from `story.json` (`chapterCount`), "has ended" from `chapter.md`, "summarised" from the chapter's `summary.md`, "reviewed" from `review.json`, "ending" from `story.json`, and "in progress" from `draft.json`. `loadNovelState` reads them in one order and trusts each. CR-01 and CR-03 come from this. One `reconcile(story)` in `src/lib`, run on load, could derive `chapterCount` from the chapter folders and fill gaps. That would make each step safe to repeat.
- **The setting lock is enforced only in the UI.** `saveSetting` (`setting.ts:204`) does not check `isSettingLocked`; the page disables the form. A later caller, such as phase 6's randomizer or a "reset to defaults" button, could write a locked setting. Moving the check into `saveSetting` keeps spec 8.1 in the logic layer, as testing.md section 1 asks.
- **Logic keyed on English display labels.** `prompt.ts` (POINT_OF_VIEW, CONTENT_RATING, DEATH_RULE), `novel.ts:327` (`"Never"`), `length.ts` (`"Short"`, `"Short story"`) and `scene.ts:324` (`"Inactive"`) compare stored values with English option labels. Decision 71 says "the choice values sent to the AI come in the novel's language". If phase 6 stores translated labels in `setting.md`, every one of these lookups falls back to a default without an error. Store stable keys and translate only for display and for the prompt.
- **Long sequences of writes.** `summarizeChapter`, `acceptEpilogue` and `finishChapter` each write three to five files in a row. Keep the rule "the marker file is written last" (see CR-03) in a code comment where each sequence starts, so later phases keep it.
- **Security posture is reasonable.** The key lives only in the credential store, or in sessionStorage in the preview. It is never in `app-settings.json` (there is a test for that) and never in `ai-log/`. Provider messages are cut to 300 characters. The HTTP permission allows any URL, which is needed for a user-set base URL. `tauri.conf.json` has `"csp": null`. Nothing renders HTML from the AI (no `dangerouslySetInnerHTML`), so this is not exploitable today, but a CSP that allows only `self` would make any future HTML rendering much safer: any script running in the window can call `invoke("get_api_key")`.
- **Settings writes can race.** The font-size slider calls `saveSettings` on every change without waiting for the previous write. On real files, an older write could finish last. Unconfirmed; low impact.
- **Duplicated `message()` wrappers.** Every page defines `function message(e) { return errorText(e) }`. `StoryList.tsx` and `StoryWorkspace.tsx` use `err.message` directly, so their file errors skip the plain-words mapping of `errors.ts`. Calling `errorText` everywhere would keep spec 9's wording consistent.
