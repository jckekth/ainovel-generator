# Code review: phase 7 (look and feel, v0.3) and its QA fixes

**Date:** 2026-10-30 · **Reviewer:** code-reviewer agent · **Files:** 44, the list of phase 7 files given with the task (the folder is not a git repository, so there is no diff), plus what they call where it mattered: `src/lib/endChapter.ts` (`checkProposals`, `approveProposal`, `describeField`), `src/lib/prompt.ts`, `src/lib/curatedSets.ts`, `src/lib/platform.ts`, `src-tauri/capabilities/default.json`
**Spec sections:** 3, 4, 7.5, 7.6, 8.5, 9, 10, 11, 12.1–12.4; decisions 94–121 · **Tests run:** `npx tsc --noEmit` (passes); `npm test` (554 passed); a throwaway test in `test-results/review/pick-proposals.test.ts` (run with `npx vitest run --config test-results/review/vitest.review.config.ts`) that confirms CR-01 and CR-03

## Summary

Phase 7 is in good shape. The new UI pieces clean up after themselves, the leave guard still covers the new top bar, the art fails safe, the curated fantasy sets are consistent in all three languages (each main character's race and rank are in its set's lists), and the QA fixes hold. The biggest risk is in the AI path, not the UI: the new `pick` fields and the class Other option are checked in the forms but not when the End Chapter call proposes changes. So a story with its adventurer ranks turned off is told that `adventurer_rank` is free text, and any rank the AI makes up is accepted (CR-01). The other findings are edge cases: the Other text box closing while the user types, opening a story now needing a successful write to `story.json`, a click that skips the book opening also landing on the page, the side list's height going stale, and a placeholder check that can pass without checking anything. I did not check anything that only the real Tauri build shows (clipboard, opener, WebView2 and WebKitGTK rendering), and I did not judge the art, contrast or icon design.

## Findings

### CR-01 · Major · The End Chapter path ignores the pick lists: ranks the story turned off, or never had, are proposed and accepted

**Fixed 2026-10-30:** checkProposals and approveProposal check races and ranks against the setting's lists; with no ranks the field is left out of the prompt and every rank change is dropped (unit tests in endChapter.test.ts and fields.test.ts).

- **Where:** `src/lib/endChapter.ts:182-186` (`describeField`, case `pick`), `src/lib/endChapter.ts:290-303` and `:320-345` (`checkProposals`), `src/lib/fields.ts:257-293` (`validate` has no `pick` check), `src/lib/characters.ts:52-54` (`hiddenKeys` does not know `hideWhenEmpty`)
- **Contract:** decision 104 ("an empty list turns ranks off"), spec 7.6 (adventurer rank "Not shown when the setting has no ranks"), spec 8.5 prompt fragments ("never skipping ranks or inventing ones outside the list")
- **Problem:** When the setting has no adventurer ranks, the End Chapter prompt lists `- adventurer_rank: text` and sends every character with `adventurer_rank: ""`, which invites the AI to fill the field in. `checkProposals` then accepts any string for a pick field, because `validate` checks `rank` fields against the ladder but has no check for `pick`. Once a rank is approved, the form shows the field again, since `hideWhenEmpty` only hides it while nothing is saved. Ranks are now on for that character in a story that turned them off. The same gap lets through invented ranks ("Platinum" when the list ends at Mithril), skipped ranks, races not in the setting ("Dragonkin"), and a whole list line or array ("Elves: long-lived forest folk", or `["Elves","Humans"]` coerced to "Elves, Humans"). Decision 113's leniency is about values that are already saved, not about new values from the AI.
- **Breaks when:** You make a fantasy story, clear Adventurer ranks, save, and write a chapter in which the knight wins a fight. The AI answers `{"character": "Aria", "field": "adventurer_rank", "new_value": "Silver", ...}`. The review shows "Adventurer rank: (empty) → Silver", Approve saves it, and the rank field now appears on Aria's sheet. Confirmed with the throwaway test: with `picks.adventurer_rank = []` the prompt holds `- adventurer_rank: text`, and the proposals `Platinum` (rank) and `Dragonkin` (race) both come back from `checkProposals`. The existing unit test in `src/lib/endChapter.test.ts:130` asserts the `text` line, so it locks in this behaviour.
- **Suggested fix:** Treat a `hideWhenEmpty` pick with an empty list as hidden everywhere the AI sees characters. That means `describeField` leaves it out, the character headers in both prompts leave it out, and `checkProposals` drops it. For a pick with options, `checkProposals` (and `approveProposal` for new characters) should accept only a value in the list, or the value already saved. Ideally this is one helper next to `hiddenKeys` that takes the setting, so the form, the prompts and the proposal check cannot drift apart. No spec change is needed, though a line in decision 113 saying the leniency covers saved values only would help.
- **Test to add:** U-EC: "fantasy with no ranks: the End Chapter prompt has no adventurer_rank line, and a proposed rank or a race outside the list is dropped; a rank in the list is kept."

### CR-02 · Minor · The Other text box closes while the user types a class that starts with an option's name

**Fixed 2026-10-30:** ChoiceWithOther keeps the typed text and whether the box is open in its own state; E2E-50 types "Mage hunter" key by key.

- **Where:** `src/components/FieldForm.tsx:242-264` (`ChoiceWithOther`)
- **Contract:** spec 7.6 / decision 105 ("Other opens a text box that must be filled"), decision 114
- **Problem:** Whether the box is open is worked out from the value alone: `typed = value !== other && !options.includes(value)`. As soon as the typed text exactly matches an option, the value is treated as that option, so the box unmounts and focus is lost. Typing "Other" itself also empties the box, because the input shows `""` whenever the value equals the Other option.
- **Breaks when:** You pick Other for class and start typing "Mage hunter". After "Mage" the box disappears, the dropdown shows Mage, and the next keystrokes go nowhere. The same happens with "Knight-errant", "Bard of…", "Ranger scout" and "Healer…" (the options are capitalised, so typing in lowercase hides the problem).
- **Suggested fix:** Keep "the box is open" as local state, set when Other is picked and cleared only when another option is picked from the dropdown. Keep the decision 114 rule (save the typed text) as it is.
- **Test to add:** E2E-50 addition: "pick Other, type 'Mage hunter': the box stays open and 'Mage hunter' is saved."

### CR-03 · Minor · AI proposals for class skip its own rules: non-strings become "[object Object]", and an empty value clears the main character's required class

**Fixed 2026-10-30:** a proposal may not empty a field the character must have, and an object becomes the field's default (unit tests).

- **Where:** `src/lib/endChapter.ts:295-303`, `src/lib/fields.ts:124` (`coerce` default) and `:287-291`, `src/lib/endChapter.ts:521-524` (`approveProposal` saves a change without the required check)
- **Contract:** spec 4 / 7.6 ("The main character must have a class"), decision 114
- **Problem:** A choice field with an `otherOption` accepts any value that is not the Other option itself. `coerce` turns whatever the AI sent into a string first, so objects, booleans, numbers and arrays all pass. `checkProposals` also validates with an empty `required` set (on purpose, so a list can be emptied), so a `null` or `""` class passes. Approving it then saves a main character without the field the story type requires. This existed before for cultivation's `special_ability`; phase 7 adds class as a second required field on this path.
- **Breaks when:** The AI answers `"new_value": {"name": "Mage"}` and you get "Class: Knight → [object Object]". Or it answers `"new_value": null` and you get "Knight → (empty)"; Approve saves the main character without a class, and every later block prompt sends `class: ""`. Both are confirmed in the throwaway test. You can work around it by rejecting the card.
- **Suggested fix:** In `checkProposals`, drop non-string values for choice fields before `coerce`. Pass the character's own `requiredKeys` for scalar fields (keep lists exempt), so a required field cannot be emptied.
- **Test to add:** U-EC: "a proposal that empties the main character's class or special ability, or sends an object for class, is dropped."

### CR-04 · Minor · Opening a story now needs a successful write to `story.json`

**Fixed 2026-10-30:** a failed write of the opened time falls back to reading the story.

- **Where:** `src/lib/stories.ts:117-121` (`markOpened`), `src/pages/StoryWorkspace.tsx:66-76`
- **Contract:** decision 115 (opening only records `openedAt`), spec 9 (file errors in plain words, reading a story should not depend on writing it)
- **Problem:** The workspace now loads the story through `markOpened`, which is a read-modify-write of the whole `story.json`. If the write fails (disk full, the file locked by antivirus or a backup tool, a read-only data folder), the story cannot be opened at all and the user sees the open error, even though nothing needed changing. Before phase 7, opening only read the file. `story.json` is also written in place without a temporary file, so writing it on every open slightly raises the chance that a crash mid-write leaves an unreadable `story.json`. `listStories` then hides that story from the shelf without a word.
- **Breaks when:** You make `stories/<id>/story.json` read-only (or fill the disk) and click the book. You get "Could not open the story" instead of the story.
- **Suggested fix:** Read with `getStory` and show the story, then record `openedAt` best-effort (`markOpened(...).catch(() => {})`). In the longer run, write `openedAt` somewhere that cannot clobber the other fields. Today the only other writers of `story.json` run behind dialogs or are repaired by `reconcileStory` (decision 75), so the race is benign. That holds only as long as nobody adds a `story.json` write outside a dialog.
- **Test to add:** U-SR: "a story whose story.json cannot be written still opens; openedAt is just not updated."

### CR-05 · Minor · A click that skips the book opening also lands on the page underneath

**Fixed 2026-10-30:** the opening ends on a click on the book itself, which covers the page, and on any key.

- **Where:** `src/components/BookOpening.tsx:22-33`, `src/styles.css:1669` (`.book-opening { pointer-events: none }`)
- **Contract:** spec 12.4 ("a click skips it", "animation never delays … a click")
- **Problem:** The overlay ignores the pointer, and the capture listener ends the animation without stopping the event. So the click meant to skip the animation is also delivered to whatever the workspace has drawn below it by then (the "All stories" back button, a tab, Write). The intent is that the skip is free. In practice, a skip that also acts is surprising. E2E-54 clicks at (10, 300), an empty spot, so it does not show this.
- **Breaks when:** You open a story with motion on and click near the top left to skip the opening. The story loads under the cover in a few milliseconds, the same click hits "All stories", and you are back on the shelf.
- **Suggested fix:** Either let the overlay take the pointer (`pointer-events: auto` and end on its own `pointerdown`, so the first click only skips), or keep things as they are and write in spec 12.4 that the click goes through. That is a product choice for the author.
- **Test to add:** E2E-54 addition: "a click on the Back button's position during the opening ends it and stays in the story" (if the first option is chosen).

### CR-06 · Minor · The wide chapter list's height is only worked out on scroll and resize, so it goes stale when the Novel tab is shown again

**Fixed 2026-10-30:** the list is not measured while its tab is hidden, and a ResizeObserver fits it again when the tab is shown.

- **Where:** `src/pages/NovelTab.tsx:400-414`
- **Contract:** spec 12.1 / decision 108 (the list opens scrolled to the current chapter), QA-02 (the list ends at the bottom of the window)
- **Problem:** `fit()` runs once on mount and then on every `.main` scroll and window resize, including while the Novel tab is hidden. A hidden element's `getBoundingClientRect().top` is 0, so a scroll on the Characters or Setting tab sets `maxHeight` to `innerHeight - 16`. Coming back to Novel fires neither event, so the list runs past the bottom of the window until the user scrolls. That is the QA-02 symptom. The effect also forces a layout read and a style write on every scroll event of every tab. Unconfirmed in the browser preview: whether switching tabs happens to fire a scroll (when the page height shrinks and the scroll position is clamped) depends on the page lengths.
- **Breaks when:** In a story with 30 chapters and a long chapter in progress, you scroll down a long character sheet on the Characters tab, then click Novel. The last chapters and the current one sit below the window edge.
- **Suggested fix:** Skip `fit` while the list is not displayed (`nav.offsetParent === null`), and run it again when the tab becomes visible, for example with a `ResizeObserver` or `IntersectionObserver` on the nav. Simpler still, give the list `max-height: calc(100vh - <its sticky top> - 16px)` in CSS, since it is sticky.
- **Test to add:** E2E-53 addition at 1200 px: "after scrolling the Characters tab and returning to Novel, the current chapter in the list is within the window."

### CR-07 · Minor · The placeholder check passes without checking anything if `about.config.ts` is reformatted

**Fixed 2026-10-30:** the check imports the config and reads the values (`placeholdersLeft`, tested in src/about.test.ts).

- **Where:** `scripts/check-about.mjs:9-11`
- **Contract:** spec 10 / decision 94 ("the installer build stops … naming each placeholder still left")
- **Problem:** The script finds the list with the regex `PLACEHOLDERS = \[([^\]]*)\]` and the entries with `"([^"]+)"`. If either stops matching, `placeholders` is empty and the script prints "About page values are set.", so the check fails open. That happens with a type annotation (`PLACEHOLDERS: string[] = [...]`), single quotes (a Prettier `singleQuote` setting), or `as const` on a renamed export. Separately, the values part is "everything before `export const PLACEHOLDERS`", which includes comments, so the word TODO in a doc comment stops the build. That one fails safe but is confusing. Nothing tests the script (testing.md lists it as manual).
- **Breaks when:** You change the line to `export const PLACEHOLDERS: string[] = ["example.itch.io", ...]` and run `npm run tauri build`. The installer builds with `https://example.itch.io/...` on the About page.
- **Suggested fix:** Fail when no placeholder list is found. Better still, keep the values in `src/about.config.json`, imported by both the page and the script, and compare the values themselves rather than the file text.
- **Test to add:** U-AB (new): "check-about exits 1 with each placeholder named for the current config, and exits 1 when it cannot find the placeholder list."

### CR-08 · Nit · The character card shows the class in English in a Chinese UI

**Fixed 2026-10-30:** the card shows a listed class in the UI language.

- **Where:** `src/pages/CharactersTab.tsx:153-158` (`summaryLine`)
- **Contract:** spec 11 ("a choice is saved in English and shown in the UI language")
- **Problem:** `v.class` is shown raw, so a 简体中文 UI reads "Knight · …" on the card while the form and the review show 骑士. The other values on that line (rank, occupation, relationship) are text, so class is the first choice field to appear there.

### CR-09 · Nit · The version is typed in three files, and About reads a different one from the installer

**Fixed 2026-10-30:** tauri.conf.json reads its version from package.json.

- **Where:** `package.json:4`, `src-tauri/tauri.conf.json:4`, `src-tauri/Cargo.toml:3`, `vite.config.ts:10`
- **Contract:** spec 10 ("version read from the build, not typed"), phase 7 acceptance check 7 ("the version matches the installer")
- **Problem:** About shows `package.json`'s version, while the installer name and the Windows file version come from `tauri.conf.json`. QA-06 needed both bumped by hand, and they will drift again.
- **Suggested fix:** Set `"version": "../package.json"` in `tauri.conf.json`, which Tauri 2 supports. Cargo's version only affects the crate.
- **Test to add:** C-CFG: "tauri.conf.json takes its version from package.json."

### CR-10 · Nit · A form error on class Other focuses the dropdown, and the text box is not linked to the error

**Fixed 2026-10-30:** while the Other box is open, the error is on the box, so a failed save focuses it.

- **Where:** `src/components/FieldForm.tsx:57-65` (`focusFirstError`), `:255-265`
- **Contract:** spec 12.2 / general accessibility
- **Problem:** The select comes first in document order and also has `aria-invalid`, so Save moves focus to the dropdown rather than to the box the user must fill. The box has `aria-invalid` but no `aria-describedby`, so a screen reader does not read the "type the class" error on it.
- **Suggested fix:** For an otherOption field holding Other, give the error to the box: `aria-describedby`, and `aria-invalid` on the box only.
- **Test to add:** E2E-50 addition: "Save with Other and an empty box puts focus in the box."

## Structure notes

- **One rule, three places.** Whether a field is hidden is now decided in three places: `hiddenKeys` (hideForMain), `CharacterForm` (hideWhenEmpty, with the setting) and nowhere in the prompts. CR-01 comes from this split. One `hiddenFor(fields, character, setting)` in `src/lib` used by the form, both prompts and `checkProposals` would keep them in step as more genres add list-driven fields.
- **The two halves of validation have drifted.** `validate` serves both the forms and the AI proposals, but the proposals need a stricter check for list-driven values (pick) and the forms need a looser one (keep what is saved). A small `checkAiValue(field, value, ctx)` beside `validate` would make the difference explicit, rather than passing an empty `required` set and relying on `rankOptions`.
- **Whole-file writes to `story.json`.** `markOpened` and `updateStory` both rewrite the whole of `story.json` from a fresh read, so the last writer wins. This is safe today only because the other writers run behind dialogs or are repaired by `reconcileStory`. If more writers are added (for example, Phase 8 storing image settings per story), a per-story write queue in `stories.ts` would make this safe for good.
- **Animation listeners are tidy.** `BookOpening`, the book menu, the Chapters panel and `About` all remove their listeners and timers, and nothing leaks across navigation. `CharacterFigure` creates a new `Image` per gender change without cancelling the old one, which is harmless with three local files. The side list's scroll listener (CR-06) is the only one that does work on every scroll.
- **`exampleMainCharacter` before the setting loads.** On a very fast click, "Create main character" can run while `setting` is still `undefined`. The set's rank then comes through even with ranks cleared (the QA-03 case). This is very unlikely; disabling the button until the setting is read would close it.
- The fantasy sets are consistent: in all 12 set and language pairs, the main character's race and rank are in that set's lists, and the config test at `src/test/storyTypes.test.ts:280` guards it.

## Docs drift

- **Spec 12.2 spine titles:** it still says a title too long for the spine ends with "…". Decision 121 says a vertical Chinese title ends with "︙" after 7 characters, as `spineTitle` does. The newest decision wins, so the spec should be updated.
- **Spec 12.4:** it says a block's text fades in "line by line". `Paragraphs` fades in each paragraph (split at blank lines), so a long paragraph streams in with no further fade. Either is fine; the spec should say which.
- **Decision 120:** it says ended chapters in the side list "show an open-book (read) icon". The icon has `opacity: 0` until hover, focus or the active item (`src/styles.css`, `.chapter-read`).
- **Decision 113 / spec 7.6:** "a value no longer in the list is kept and shown as saved" does not say whether AI proposals may add values outside the list (see CR-01). The unit test at `src/lib/endChapter.test.ts:130` enshrines `adventurer_rank: text` for an empty list, against decision 104.
- **`playwright.config.ts:21`:** the comment says "E2E-50 checks animation with motion on"; decision 117 and testing.md say E2E-54.
- **docs/tech:** it was last checked on 2026-10-18. `architecture.md:56` still describes "the side rail", and `architecture.md:97` says the version lives in four places including a rail footer in `App.tsx`; it is now three files, and About reads it from the build. None of the phase 7 modules (`art.ts`, `about.config.ts`, the pick type, `BookOpening`, the bookshelf) are described yet.
- **Decisions 97 and 99** still describe three figures per type and fantasy knight, healer and mage figures. They are superseded by decision 103, which says so, so this is not wrong, but a "(replaced by 103)" note on those rows would save a reader the trip.
